# UI components

- Always build UI out of the primitives in `components/ui/` (`Button`, `Input`, `Field`, `Label`, `Checkbox`, `Alert`, `Badge`, `Tabs`, `Select`, `Textarea`, `Tooltip`, `Vault`, etc.). Do not drop down to raw `<button>`, `<input>`, `<label>` when an equivalent already exists there — add a variant or prop to the shared component instead of styling a one-off element inline.
- The app's "Organic" theme (warm surfaces, pill-shaped controls, orange primary/accent) comes in **light and dark**. `:root` in `app/globals.css` holds the light palette, `.dark` overrides it; `next-themes` (`components/providers/theme-provider.tsx`, `attribute="class"`, default `"system"`) puts the class on `<html>`, and the user picks Sistema/Claro/Escuro in Settings → Aparência (`components/settings/theme-toggle.tsx`; stored per device in localStorage). Tailwind's `dark:` variant is remapped to that class via `@custom-variant` — it does NOT follow `prefers-color-scheme` on its own.
  - Tokens: `--background`, `--card`, `--popover`, `--primary`, `--accent`, `--success`, `--destructive`, `--warning`, `--info`, `--publication`, `--border`, `--input`, `--secondary`, `--muted`, `--ring`, `--surface`, `--surface-elevated`, `--sidebar` (sidebar + desktop side panels), `--glass` (frosted composers/dropdowns, used at `/90`–`/95`), `--shadow`/`--shadow-strong` (use as `shadow-[0_12px_36px_var(--shadow)]`). Never hardcode hex colors, `white/…` borders/fills or `rgba(0,0,0,…)` shadows in components — they only work on one of the two palettes. For neutral translucent fills use `foreground/5`, `foreground/10`. Literal `bg-black/…` + `text-white` is fine only over video/thumbnails and as a modal backdrop.
  - **Contrast is a hard rule**: every text token clears WCAG AA (4.5:1) on every surface, its own `/15` tint included, in both palettes (the ratios are in the comment above `:root`). When adding or retuning a colour, re-check it in both themes. In light mode the oranges are darkened for text, so `bg-accent`/`bg-primary` there are dark fills — pair them with `*-foreground`, never `text-foreground`/`text-background`. `<mark>`-style `text-accent` on `bg-accent/N` must stay at `/15` or lighter (`/25` drops to 4.2:1 on light).
  - Handwriting: the two neutral inks (`INK_COLORS[0]` cream, `[1]` black) mean "page text colour"/"its opposite" and swap at display time on light (`displayInkColor`, `useInkAppearance`), stored values untouched; the highlighter composites with `multiply` on light (`lighter` turns it invisible on cream). JW Library highlight colours are pastel with fixed dark text and work on both.
- Three font families are wired as Tailwind utilities: `font-heading` (Caprasimo — page titles, primary/outline CTA buttons), `font-sans` (Figtree — default body/UI text), `font-mono` (JetBrains Mono — small labels, badges, sync-status text). `Button`'s `default` and `outline` variants already apply `font-heading`; other variants stay `font-sans`.
- If a needed pattern doesn't exist yet in `components/ui/`, extend the existing component (new `variant`/`size` in its `cva` config) rather than forking it, so every consumer benefits and the design stays in one place.
- **No modal dialogs, ever — confirmations go through a Vault.** This app has no `Dialog`/`AlertDialog` component and shouldn't gain one. Any "are you sure?" moment (delete note, delete folder, bulk delete, …) uses `components/ui/confirm-vault.tsx` (`<ConfirmVault>`), which is already mobile/desktop-adaptive because it's built on `Vault`. If a new confirmation need doesn't fit `ConfirmVault`'s props, extend that component rather than reaching for a dialog primitive.

# Architecture

- Next.js App Router only, on Next.js 16 — this version renamed `middleware.ts` to `proxy.ts` and made several other breaking changes from what most training data assumes. Before touching routing, caching, or config, check `node_modules/next/dist/docs/` for the current API (see `AGENTS.md`).
- Auth is Supabase (`@supabase/ssr`), split by runtime:
  - `lib/supabase/client.ts` — browser client, for Client Components only.
  - `lib/supabase/server.ts` — server client (reads/writes cookies via `next/headers`), for Server Components, Server Actions, and Route Handlers.
  - `lib/supabase/middleware.ts` + `proxy.ts` — refreshes the session on every request and does the optimistic redirect between public/protected routes. Public routes are listed in `PUBLIC_ROUTES` in `lib/supabase/middleware.ts`.
- Mutations (sign in/up/out, and future data writes) go through Server Actions (`"use server"`), colocated as `actions.ts` next to the page that uses them (see `app/login/actions.ts`), driven from the client with `useActionState`. Prefer this over client-side `fetch` to an API route.
- Auth is email/password only — no OAuth providers (Google, etc.) are wired up, and none should be added unless explicitly requested. `app/auth/callback/route.ts` still exists for exchanging the code from Supabase's e-mail confirmation links (signup confirmation), not for OAuth.
- New protected areas of the app go under routes added to the protected side of `proxy.ts`'s route check; new public marketing/auth pages go in `PUBLIC_ROUTES`.
- Signed-in app screens live in the `app/(app)/` route group, which supplies the sidebar + assistant surface via its layout. Its pages compose `<Header variant="search|title">` + content + (where relevant) `<AssistantDock />`.
- Notes, files and folders all share the single `/notes` screen — there is deliberately **no** separate `/files` route. `<NotesCollection showFolders />` renders the folders row plus the mixed notes/files masonry; clicking a folder filters in place via local state rather than navigating.
- Notes and folders are real Postgres tables (`public.notes`, `public.folders`) — **RLS is the actual access control here**, unlike Storage (see below). Every row has `user_id`, and both tables have an owner-only `for all using (auth.uid() = user_id)` policy, so `app/(app)/notes-actions.ts` uses the regular per-request server client (`lib/supabase/server.ts`), not the admin client — Postgres itself rejects cross-user reads/writes even if a check in app code were ever missed.
- **`lib/store/notes-store.ts` is offline-first**, not just an optimistic cache: it's a zustand store wrapped in `persist` (localStorage, key `study-notes:notes`, `skipHydration: true` — rehydrated explicitly by `StoreHydration`), holding `notes`, `folders`, and a **pending-ops outbox** (`pendingOps`, keyed so a burst of edits to the same note/folder coalesces into one queued op instead of stacking). Every mutation still updates state optimistically first, then calls the matching Server Action via `runOrQueue`: a normal `{error}` response is a real rejection (rolls back + toasts, as before); a **thrown** error means the `fetch()` itself never reached the origin (offline), so the op is written into `pendingOps` instead of surfaced as a failure. `updateNote` never rolls back note text either way — discarding what the user just typed would be worse than a stale save.
  - Coalescing rules live in `enqueueOp`: a second `updateNote` for the same id replaces the first in place; a `deleteNote`/`deleteFolder` queued behind an unsynced `createNote`/`createFolder` for the same id cancels both out rather than round-tripping a doomed create-then-delete.
  - Reconnection is driven from three places in `components/providers/device-listener.tsx` (all calling `useNotesStore.getState().syncPendingOps()`, which replays the outbox in FIFO order and stops at the first op that still can't reach the server): the browser's `online` event, a `focus`/`visibilitychange` fallback (the `online` event is not reliable everywhere — confirmed empirically in Playwright's network-offline emulation, where toggling a context back online does not fire it for a page created while already offline), and a 5s `setInterval` safety net that only does anything when `pendingOps` is non-empty. `useDeviceStore.isOnline` (mirrored from `navigator.onLine`) drives the sidebar's connectivity copy; `usePendingSyncCount()` drives its "N alterações aguardando sincronização" line — this is the real `design.html` mockup's original intent for that card, not new scope.
  - `StoreHydration` calls `useNotesStore.persist.rehydrate()` **before** `hydrate(serverNotes, serverFolders)`, so `hydrate`'s merge can tell which ids have a pending op and keep the local version for those (including notes/folders that only exist locally — an unsynced create) instead of letting the server-fetched rows clobber an unsynced draft. Anything with a pending delete is dropped from the merge even if the server still has it.
  - **Deliberately not using `experimental.useOffline`** (Next 16's built-in connectivity-aware retry for navigations/Server Actions, `next/offline`): tried it first, but it holds a Server Action's `fetch()` pending *in memory* instead of rejecting, which defeats `runOrQueue`'s catch-based detection — nothing ever lands in the persisted outbox, so an edit made offline is lost for good if the tab closes before reconnecting (verified this empirically before reverting). Our own outbox is strictly more durable for this app's requirement (drafts must survive a closed/reloaded tab), so the flag stays off.
  - **The `(app)` layout is a static, fetch-free shell.** Notes/folders/tags, conversations and preferences are loaded client-side by `StoreHydration`/`ChatHydration` (Server Actions on mount, retried with backoff), painting first from the persisted local store; `hydrated` flips true immediately when something is cached, else after the first server answer (or after the first failed attempt). It used to `await listUserContent()` in the layout, which made the whole subtree dynamic so `/notes/new` needed an RSC round trip and a cold-offline session showed nothing. **Don't reintroduce a server fetch or `cookies()` read in that layout** — `/notes/new` is now prerendered (`○` in the build table). The layout wraps `children` in one `<Suspense>` because several pages call `useSearchParams()`, which a static prerender requires. `/notes/[id]` stays dynamic (`getPublication`), so opening an existing note from a cold-offline session still needs the cached RSC.
- **Schema changes go through `scripts/db-migrate.mjs`**, which applies any new `.sql` file in `supabase/migrations/` (tracked in a `public._migrations` table, filename order, one transaction each) using `DATABASE_URL` — a direct Postgres connection string (Project Settings → Database), not the Supabase REST API, since RLS policies and other DDL aren't reachable through `service_role`/PostgREST. Add a new numbered file rather than editing an applied one. Run it with `npm run migrate`.
- Initial notes/folders are fetched **server-side** in the async `app/(app)/layout.tsx` (via `listUserContent()`, RLS-scoped to the signed-in user) and passed into `<StoreHydration>`, which seeds the zustand store once on mount. `useHydrated()` reflects the store's own `hydrated` flag, not "some component mounted" — child effects fire before parent effects in React, so a mount-based flag in a child could (and did, before this was fixed) flip true before the parent's seeding effect had actually run.
- **Notes are rich text**, via Tiptap (`components/content/rich-text-editor.tsx`), storing HTML in the same `notes.body` column that used to hold plain text (no migration needed — Tiptap renders plain text as a single paragraph, so old notes still load fine). Formatting is a **floating `BubbleMenu`** (from `@tiptap/react/menus`, not a fixed toolbar) that appears on text selection: bold, italic, task list, and text-align left/center/right/justify. Image insert lives as a persistent header button next to the pin button in `note-editor.tsx` (not the bubble menu, which only shows when text is selected) — plus paste and drag-and-drop, both handled in `editorProps.handlePaste`/`handleDrop`.
  - `TaskList`/`TaskItem` **must** come from `@tiptap/extension-list`, not the older standalone `@tiptap/extension-task-list`/`@tiptap/extension-task-item` packages — StarterKit already wires up `@tiptap/extension-list`'s `ListKeymap`, which those standalone packages don't share, and without it Enter did nothing inside a bullet/ordered list item (not applicable to `taskItem` either way, see the known gap below).
  - **Known gap, verified not worth the fix cost**: pressing Enter while the cursor is inside an existing task item does not create a new task item (`editor.commands.splitListItem("taskItem")` returns `false` even with a cleanly collapsed selection — reproduced directly against the editor instance, not a test artifact). The working pattern instead: type each item as its own line first, then select all of them and toggle "Lista de tarefas" once — `toggleTaskList` correctly turns every selected paragraph into its own item. Enter still works completely normally everywhere else (plain paragraphs split fine).
  - Images upload through `app/(app)/note-images-actions.ts` (`uploadNoteImage`) to a **second, public-read** Storage bucket, `note-images` — deliberately separate from the private `files` bucket below, because an inline `<img src>` needs a stable long-lived URL and `files`' signed URLs expire in 60s. Public read only; writes still require the service-role client (`createAdminClient()`), same ownership-by-path-prefix convention as `files`. Provisioned via a one-off script (not a SQL migration — Storage buckets aren't DDL) with `public: true`.
  - **Orphaned images are cleaned up**, via `lib/note-images.ts` (`extractNoteImagePaths`/`removedNoteImagePaths` — regex-based, not `DOMParser`, since this needs to run server-side too) and `deleteNoteImages` in `note-images-actions.ts`: deleting a note (`deleteNotePermanently`/`bulkDeleteNotesPermanently` in `notes-actions.ts`) removes every image still referenced in its body; editing a note's body (`updateNote` in `notes-store.ts`) diffs the old vs. new body **client-side** (both are already in memory there, avoiding an extra server round trip on every autosave) and deletes whatever image got removed from the text. Both are best-effort and fire-and-forget — not part of the offline outbox, since a failed cleanup just leaves an orphaned object (reclaimable bytes), never lost note content, so it doesn't need the outbox's retry/durability guarantees.
  - Card previews (`components/content/note-card.tsx`) parse the HTML body client-side via `lib/note-preview.ts` (`DOMParser`, safe here since `NoteCard` only ever renders after the notes store has hydrated, i.e. always client-side) into whichever of three views a card shows: a Keep-style checklist (up to 5 items, "+N mais" beyond that, struck-through when checked) if the body contains a task list; a leading image thumbnail if it contains an image and no task list; otherwise a truncated excerpt that **preserves inline formatting** (`truncateToHtml` walks the DOM keeping `<strong>`/`<em>`/etc. intact instead of just reading `textContent`, then it's rendered via `dangerouslySetInnerHTML` — safe here since the body is Tiptap-schema HTML, the same trust level `NoteEditor` already renders it at, not arbitrary markup). File-type cards (PDF/DOCX/etc.) skip all of this — their `body` is a plain one-line size string like "2.3 MB", never HTML.
  - Checklist items are **directly clickable from the card preview** (`onToggleChecklistItem` prop, wired through `notes-collection.tsx` to `useNotesStore.toggleChecklistItem`, which flips the item's `data-checked`/`checked` attributes via `lib/note-preview.ts`'s `toggleChecklistItemInHtml` and reuses `updateNote`'s normal offline-safe save path). Each item is its own `<button>`, structurally a **sibling** of the card's title-opening `<button>` — not nested inside it — specifically so clicking a checkbox can never also trigger "open the note" and so the markup stays valid (a checkbox can't nest inside another button).
  - The editor's task-item checkbox is a custom React node view (`components/content/task-item-node-view.tsx`, wired via `TaskItem.extend({ addNodeView: () => ReactNodeViewRenderer(...) })` in `rich-text-editor.tsx`) using the app's own animated `Checkbox` primitive (`components/ui/checkbox.tsx`) instead of Tiptap's default bare native `<input type="checkbox">`. `NodeViewWrapper` must be given `as="li"` — its default tag is `div`, which would break the list's actual DOM structure.
- **Any note can carry handwriting and a voice recording synced to it** — the Samsung Notes model: one note holds typed text *and* ink, and playing the recording replays the ink in the rhythm it was written. There is deliberately **no separate "drawing note" type** (migration `0040` added one, `0041` removed it again — making the user choose between a text note and a drawing note up front was the wrong split, and nothing was lost folding them back since strokes are keyed by `note_id`, not by type).
  - It's all `NoteEditor`: a pen toggle in the header turns the ink layer on, which puts `DrawingToolbar` inline in the sticky header itself (costing the note no vertical space) and lets `DrawingCanvas` take pointer events. The toolbar shows only what's chosen constantly — tool, undo/redo, record, the player — with ink colour and thickness behind the swatch that already displays the current one, and pen-only/clear behind an overflow menu; laying all of it out in a row made the header an unusable strip. Share and image-insert hide while the pen is out, since they belong to typing. Toggled off, the canvas keeps showing the ink but is `pointer-events-none`, so typing works exactly as before, and an `AudioLines` button beside the pin plays a recording back without picking the pen up.
  - **`DrawingCanvas`'s wrapper must stay `pointer-events-none`** — it spans the whole note, so with the default it silently swallowed every tap meant for the text and made notes impossible to type in. Only the live canvas opts back in, and only while drawing is active.
  - **Running out of room is not a gesture.** Samsung Notes has you drag the page up to add one; here the note just keeps `60svh` of blank space below whatever is lowest on it while the pen is out. Writing toward the bottom extends the page by itself, there is no page boundary to manage, and the space collapses when the pen is put away so a typed note is never padded with emptiness. It's two deliberately separate, non-circular pieces: `inkMinHeight` (from `lowestInkY`, so it keeps room under the lowest *stroke*) and a spacer element at the end of the text column (room under the *text*).
  - **Never size the ink wrapper from a measurement of anything inside it.** The text column is `flex-1`, so it stretches to the wrapper — deriving the wrapper's height from the column's measured height is a ResizeObserver feedback loop, and it shipped once: the note grew without bound, scrolled by itself and crashed the browser on a tablet. The wrapper's `ResizeObserver` reads **width only**; height comes from the strokes, which layout can't change.
  - **The canvas backing store is capped at `MAX_CANVAS_PIXELS`** (~12 MP a layer). The ink layer is as tall as the note, so at native `devicePixelRatio` a few screens of writing on a 3x tablet asks for hundreds of MB per layer — past what the browser will allocate (it hands back a blank canvas) and enough to kill the tab. The live layer also clears only the in-progress stroke's bounding box (`liveDirtyRef`) rather than wiping a canvas several screens tall on every `pointermove`.
  - Strokes live in `public.note_drawings`, **not** in `notes.body` — a page of handwriting is hundreds of KB of vector data, and `notes.body` is what feeds card previews, search and vectorization. Encrypted with the same `encryptText`/`decryptText` as note text.
  - `lib/drawing/strokes.ts` is the whole model: points are `[x, y, pressure, dt]` tuples (names would triple the payload at tens of thousands of points per note) in a logical space whose **width** is always `PAGE_WIDTH`, with height unbounded — the ink layer is as tall as the note it covers, so it grows as the user writes rather than being a fixed page. `dt` is ms since the stroke began and `Stroke.t` is ms into the recording — together they're the only timeline, which is what makes `renderStrokes(ctx, strokes, revealUntilMs)` serve both normal display and audio-synced replay. A stroke written with no recording running has no `t` and is always visible.
  - The canvas is two stacked `<canvas>` layers — committed ink below, the in-progress stroke above — so a live stroke never redraws the whole note. It reads `getCoalescedEvents()`, since a stylus reports far faster than pointermove fires.
  - **Palm rejection is an explicit toggle**, `penOnly` in `lib/store/preferences-store.ts` — client-only on purpose (same reasoning as `jwlibraryViewMode`): whether there's a pen is a property of the *device*, not the account. It auto-enables the first time a `pointerType === "pen"` event arrives and the toolbar's own button overrides it either way — auto-detection alone was wrong, because a stylus the browser doesn't report as a pen would leave the user with no way to ask for the mode. On: only the stylus draws and touch scrolls the note. Off: touch *is* the pen, so scrolling means leaving pen mode — the unavoidable tradeoff on a device with no stylus. A mouse draws in either mode; this is about a resting palm, not about pointing devices.
  - **The ink layer keeps `touch-action: none` in both modes, and pen-only mode scrolls the page by hand** (`scrollableAncestor` + `scrollBy` in `drawing-canvas.tsx`). `touch-action: pan-y` looks like the obvious way to let touch scroll, but it can't be narrowed to one pointer type: the browser applied it to the *stylus* too, decided a pen drag was a scroll and cancelled the pointer stream a few pixels in, so handwriting came out as disconnected dots (reported on a Galaxy Tab S6 Lite; the pen itself was being reported as `pointerType: "pen"` correctly). Manual scrolling loses fling, which is the cheaper cost. **Don't reintroduce `pan-y` here.**
  - `NoteEditor.ensureNote()` is the single note-creation path: typing, drawing and hitting record all go through it, so they can't race each other into two separate notes.
  - Audio uploads **direct to Storage from the browser** via a service-role-issued signed upload URL (`requestAudioUploadSlot` → `uploadToSignedUrl` → `finalizeAudioUpload`), the same two-step shape as `requestFileUploadSlots` in files-actions.ts — a recording routinely passes Vercel's ~4.5 MB Serverless request-body cap, which `serverActions.bodySizeLimit` cannot raise. The private `note-audio` bucket is provisioned by `scripts/create-note-audio-bucket.mjs` (buckets aren't DDL, so not a migration). Safari/iOS only produces `audio/mp4`; everything else gets WebM/Opus, and the `;codecs=opus` suffix is stripped before upload or the bucket's `allowedMimeTypes` check rejects it.
  - **A recording can be paused and resumed** (`MediaRecorder.pause()`/`resume()`), for a lesson that stops and picks up later. `useAudioRecorder` therefore sums elapsed time **per segment** rather than measuring from a single start — a wall-clock elapsed would drift past the audio by however long the pause lasted, and every stroke stamped after that would replay at the wrong moment. Ink written *while paused* is stamped at the moment the audio stopped, so it belongs to that point in the recording rather than falling outside the timeline. Pause/resume is within one editing session: leaving the note closes the take out (`leaveNote`) and uploads it, and a `beforeunload` guard asks before a reload discards one. Appending to an existing recording on a later visit is **not** supported — that needs real audio concatenation, not `resume()`.
  - **MediaRecorder's WebM declares no duration**, so the element reports `Infinity` and refuses to seek — `note-editor.tsx` forces a scan on `loadedmetadata` (`currentTime = 1e101`, then back to 0). The seek bar itself is driven by the `audio_duration_ms` measured at record time, never by `audio.duration`.
  - Ink saves go through the notes store's **offline outbox** like every other mutation (`saveDrawingStrokes` → a `saveDrawing` op keyed `drawing:<id>`, one slot per note since the layer is saved whole). The `createNote` op is enqueued first, so FIFO replay creates the row before its strokes land.
  - **Known gaps, deliberate for now**: the eraser removes whole strokes rather than pixels; ink is positioned in the layer's own coordinates, so reflowing text (a very different screen width) moves the text under the ink rather than with it; card previews don't show a thumbnail of the ink; and the recording syncs to *handwriting* only — typed characters are not on the audio timeline.
- **PDFs are drawn by pdf.js, not an `<iframe>`, and can be written on.** `components/content/pdf-pages.tsx` renders each page into a `<canvas>` (`pdfjs-dist` legacy build, worker emitted by Turbopack via `new URL(..., import.meta.url)`). The iframe only ever worked on desktop — Android Chrome has no inline PDF viewer and showed "Este conteúdo está bloqueado". The file is fetched whole (`disableRange`/`disableStream`) because the signed URL lives 60s and a later range request would be refused; only pages near the viewport hold pixels. Handwriting reuses the note ink model: `Stroke.page` tags each stroke, strokes go to `note_drawings` through the same offline outbox (`saveDrawingStrokes`), and each page has its own `DrawingCanvas` forced to `appearance="light"` (a page is white paper in either theme). The PDF itself is never modified — annotations are a vector overlay. **Known gap**: no export of the annotated PDF, and ink is stored in page-relative units so it follows a page when the width changes.
- The assistant (`components/assistant/`) is UI-complete but talks to a **placeholder** server action (`app/(app)/assistant-actions.ts`) — no AI provider key is configured. It still verifies the Supabase session server-side, and returns the `AssistantReply` shape the real RAG call should keep.
- Uploaded files are real, in Supabase Storage — the private `files` bucket (`user_id/uuid-filename` paths, no bucket-level RLS policies since every access goes through the service-role client server-side; verified empirically — direct anon upload/list/download attempts against the bucket all fail even with a real object present, since `storage.objects` RLS defaults to deny-all with zero policies). `app/(app)/files-actions.ts` has the only code allowed to touch it: `uploadFiles` (validates size/extension/rate-limit, uploads, then inserts the matching `notes` row via the regular per-user client in the same call), `getFileUrl` (60s signed URL), `deleteStorageFile`. All three re-verify the session and check the path is prefixed with that user's id before doing anything — the bucket has no RLS of its own, so this ownership check *is* the access control for Storage specifically (contrast with notes/folders above, where RLS itself is the control). `hooks/use-file-upload.ts` is the one client entry point (used by the mobile upload button and desktop drag-and-drop); everything else (limits, bucket name) lives in `lib/storage-config.ts`. Size limits are per-extension via `maxSizeForExtension()` — `.jwpub` gets 50 MB (a whole publication) against the 15 MB default. **50 MB is Supabase's project-wide Storage ceiling on the current plan** (the `files` bucket's own `file_size_limit` can't be set higher — `updateBucket` rejects it, verified), so a `.jwpub` bigger than that (e.g. "Ande Corajosamente com Deus", 80 MB) takes the **parse-only path**: `isParseOnlyJwpub` → `createParseOnlyJwpubNote` creates just the note row (no `storage_path`) and the browser parses the local file into the database as usual; the original archive simply isn't kept, so the reader's ↻ asks for the file again via a picker instead of re-downloading it (`JWPUB_PARSE_ONLY_MAX_SIZE`, 200 MB, is browser memory, not storage). Raising the Storage limit in the Supabase dashboard (paid plans) would make this unnecessary.
- **Highlight colours carry user labels** (Settings → Destaques, up to 3 words each), stored in `preferences.highlightLabels` (`lib/jwlibrary/highlight-labels.ts`, mirrored in the preferences store). Every colour button is `components/ui/highlight-swatch.tsx` (tooltip = label, else colour name) — never draw a swatch by hand.
- **Side panels mark text too.** `SidebarHighlightedHtml` (excerpts, references, appendices, WOL articles/snapshots) creates highlights and notes with everything swapping *inside* the panel (`InlineHighlightNote`) — never a second panel or the editor Vault. Location columns come from `resolveDocumentLocation`; `getChapterHighlights` therefore matches by MepsDocumentId + language only, not symbol/issue. `HighlightableHtml`'s colour pill is positioned `absolute` inside its wrapper because `fixed` breaks inside a Vault.
- **Tab in the editor is two-stage** (`lib/tiptap/paragraph-indent.ts`): first-line indent (`firstLine` → `text-indent`), then paragraph indent (`indent` → `margin-left`); Shift-Tab takes a margin level back, then the first-line space; Backspace at the start removes the first-line space first (the paragraph stays indented), then margin levels. The PDF export honours both.
- **A note has an optional heading list** (`components/content/note-outline.tsx`, header button, `showOutline` per device): built from the top-level headings, a column centred in the left margin when `<main>` is ≥ 1120px, a Vault otherwise. Its "Recolher/Expandir tudo" sets the same `collapsed` attribute as the chevrons (hidden on phones, where collapsing is off).
- **`.jwpub` publications are read in-app, not downloaded.** A `.jwpub` is a zip wrapping a SQLite database (sometimes nested inside a `contents` entry that is itself a zip) plus media; `Document`/`Footnote` blobs are AES-CBC encrypted then deflated, keyed by `SHA-256("{MepsLanguageIndex}_{Symbol}_{Year}[_{IssueTagNumber}]")` XOR a fixed constant (bytes 0..16 = key, 16..32 = IV — and the `_{IssueTagNumber}` segment is omitted when it's 0, which is the single easiest thing to get wrong).
  - **Parsing runs in the browser** (`lib/jwpub/`), because it needs `DOMParser` — which Node lacks — plus `sql.js`/`pako`/`crypto.subtle`, and because re-sending a 60 MB archive to the server would be a second upload. `jszip`/`sql.js`/`pako` are pulled in *only* via `await import(...)` inside `lib/jwpub/parser.ts` (the repo's only dynamic import), so they land in a lazy chunk the reader never loads — verified absent from `build-manifest.json`'s root files.
  - **Ingest is fire-and-forget from `hooks/use-file-upload.ts`**, after `uploadFiles` + `addFiles` have already put the card on screen. That ordering is deliberate: the note row and Storage object exist before parsing starts, so any parse failure just leaves a normal file card plus a `status = 'failed'` publication row, and the reader offers "Processar publicação" — which re-downloads via `getFileUrl` and re-runs the same `ingestJwpub`. That retry is also the path for files uploaded before this feature existed.
  - Parsed content lives in `jwpub_publications` / `jwpub_chapters` / `jwpub_footnotes` (migration `0002`), **deliberately unencrypted** unlike `notes` — public publication material, still RLS-scoped per owner. Everything cascades from `notes.id`, so deleting a note drops the whole publication; only Storage needs the explicit sweep (`deletePublicationMediaForNote`, wired into `deleteNotePermanently`/`bulkDeleteNotesPermanently`).
  - Illustrations go to the public-read `jwpub-media` bucket under `${user_id}/${publication_id}/`, uploaded in batches of `JWPUB_MEDIA_BATCH_SIZE`, deduped by filename, and only for images a chapter actually references. **Images pulled out of a zip arrive typeless**, and Supabase validates the bucket's `allowedMimeTypes` against the blob's own type, not the `contentType` option — so `uploadPublicationMedia` re-wraps each file in a `Blob` with the extension-derived type before uploading. Without that every upload fails with `mime type application/octet-stream is not supported`.

Whatever is cached paints immediately and is re-fetched in the background; the screen updates only if the server's copy differs, so there is no invalidation protocol to maintain. `useChapterData` in `hooks/use-bible-study-data.ts` reads memory during render (no skeleton flash) and warms the next chapter 1.5 s after one settles (Server Actions are dispatched one at a time per client, hence the delay). Bump `CACHE_VERSION` there if a cached payload's shape changes. Cleared on sign-out (memory in `signOutAndWipeLocalData`, IndexedDB with the rest of the offline database).
  - *Auth* — read-only actions on public reference content use `getSessionUserId()` (`lib/supabase/auth.ts`, `getClaims()`: JWT verified locally against the cached JWKS) instead of `auth.getUser()`, which is a network round trip to Supabase Auth. It only saves time if the project signs with asymmetric JWT keys (otherwise `getClaims()` falls back to the same server call); the cost is that a session revoked elsewhere stays valid until its access token expires. Keep `getUser()` for anything that writes user data or uses the admin client on a user's behalf. `proxy.ts` still uses `getUser()`.

- **Notes and folders can be shared with other users (invite → accept), and a shared note is edited in real time.** Migration `0055_sharing.sql`; actions in `app/(app)/shares-actions.ts` and `app/(app)/collab-actions.ts`; client in `lib/collab/` and `lib/store/shared-store.ts`; UI in `components/content/share-vault.tsx` (owner) and `shared-with-me.tsx` (the "COMPARTILHADO COMIGO" pill on `/notes`, beside "PASTAS").
  - **Access is computed by the database, never copied.** `shared_note_access()` / `shared_folder_access()` / `note_share_role()` (SECURITY DEFINER, scoped to `auth.uid()`) recompute on every read: a note created or moved into a shared folder later is included, and a note that is locked — directly, or through any folder above it, including above the shared one — drops out until unlocked. Only `type = 'nota'`, `status = 'active'` notes are shared (no files/publications). Roles: `editor` / `viewer`.
  - The sharing RLS is **additive** (`notes_shared_select`, `notes_shared_update`, `folders_shared_select`), so a plain `select * from notes` now also returns notes shared with the caller. **Every query that means "my own" must filter `user_id` explicitly** — `listUserContent`, `getNoteLockState`, the folder-move check, the scripture backfill, `revectorizeAllNotes`, the drawing actions and the delete paths already do. Forget it and shared notes leak into the owner store / outbox.
  - A collaborator edits **title/body only**: `notes_collaborator_guard` (before update) rejects any other column change by a non-owner. Derived data (vectorization queue, scripture index) is always written **under the note owner's id** (`lib/notes/derived-data.ts`, service role for a collaborator's edit after RLS already let the update through) — otherwise the owner's embeddings would move to the editor.
  - Invites are by e-mail and **in-app only** (no e-mail is sent). The answer never reveals whether the address has an account; an invite to an address with no account waits, and the `on_auth_user_sync` trigger on `auth.users` attaches it at sign-up (it also keeps `public.profiles` filled). `shares_guard` lets the invitee only accept/decline/leave and the owner only change role or re-invite (back to `pending`). Revoking deletes the row.
  - **An own note is never "revoked", and a note born in an editor never turns collaborative under the user's fingers.** `note_share_role` is null for a row the server doesn't have yet, which used to lock the owner out seconds after creating a note in a shared folder. `/notes/new?folder=<own shared folder>` creates the row first and then opens `/notes/<id>?new=1`; offline it stays an ordinary editor.
  - A collaborator's caret, name tag and selection fade after 4 s without moving or typing (`lib/collab/use-idle-carets.ts`, hidden by a generated rule on `data-client`).
  - **Real-time editing is Yjs over Supabase Realtime Broadcast** — no extra server. `lib/collab/supabase-provider.ts` is a small custom provider on the **private** channel `note:<id>`: RLS on `realtime.messages` (`collab_topic_role`) lets anyone with access join and receive, and only owner/editor *send* broadcasts (a viewer sends only presence). Updates are batched (~80 ms) because Realtime bills per message (and once more per receiver); payloads over ~180 KB aren't broadcast — peers re-read the server copy after the next save (`refresh`). Join does a two-way state-vector exchange (`sync1`/`sync1r`/`sync2`), which is what brings back edits made offline.
  - **The Yjs document is the source of truth for a shared note's text; `notes.body` is a derived HTML snapshot** written with each save, so previews, search, vectorization and the scripture index keep working. State lives in `note_collab_state` (base64 Yjs update, **encrypted** like note text). `saveCollabState` **merges** (`Y.mergeUpdates`) into what's stored under an `updated_at` optimistic lock — an edit coming back from offline can never wipe out others'. The **first** open seeds the doc from the HTML with the editor's own schema; `initCollabState` stores only the first seed (`on conflict do nothing`) and everyone continues from that one — two clients seeding independently would duplicate the text. The title is a `Y.Text` in the same doc. A viewer opening a note no editor has opened collaboratively yet sees the HTML snapshot read-only.
  - Only notes that are shared (pending or accepted, directly or via a folder) go collaborative; every other note keeps the normal offline-first outbox path untouched. In `RichTextEditor` the `collab` prop swaps StarterKit's history for Yjs's and adds Collaboration + CollaborationCaret; the component is keyed on the mode because extensions only count at creation. **`editable` also only counts at creation** — a later change is pushed with `editor.setEditable` (without it the owner's editor stayed read-only after seeding).
  - **Opening, seeding and the access check go through `app/api/collab/[id]` (a Route Handler, `lib/collab/collab-api.ts`), not Server Actions.** Next runs Server Actions one at a time per client and a note page fires several on mount, so as an action the open waited in that queue — a shared note took ~5 s to appear (measured). Saving stays an action (it's in the background). The editor shows the skeleton — never an empty/stale editor that then swaps — while it can't yet rule out that a note is shared (shared lists not read back from the device yet, or a note that isn't in the user's own store), and while the first state is being seeded (the editor is mounted hidden, since it builds the seed from its own schema).
  - **Offline**: each shared note keeps a device copy in IndexedDB (`study-notes-collab:<id>`, y-indexeddb), so it opens and edits offline once it has been opened online. "Removed" means removed on the device too: every `listSharedWithMe` refresh purges the local list entry *and* that IndexedDB database for anything no longer shared, an open editor re-checks access every 30 s (and on a failed save) and closes/wipes when access is gone, and sign-out deletes them all.
  - **An editor can create notes inside a shared folder** ("Nova nota aqui" in the folder view, or the composer's "Nova nota"/drag-to-create while that folder is open — `useNewNoteFolderId()` in `folder-view-store.ts` returns the open shared folder before the own one). `createNoteInSharedFolder` inserts it **owned by the folder's owner** (service role, after `shared_folder_access()` confirms editor access to that exact folder) — that's what puts it in the shared tree for everyone and keeps it there if its creator leaves; `NoteEditor` on `/notes/new?folder=<shared>` creates it up front and replaces the route with `/notes/<id>`, so it's collaborative from the first keystroke. Online only. The owner's own list picks it up on the next focus (`refreshOwnContent`, throttled to once a minute).
  - `ShareVault` also lists people who get a note/folder **through a shared folder above it** ("PELA PASTA …", read-only — managed on that folder); `listShareMembers` returns them as `inherited`.
  - **References inside a shared note open for collaborators from the OWNER's library.** Excerpts, publication chapters (`(th 2)` / by id), `pubref` citations and "@nota" mentions point at the owner's private rows, which RLS hides from everyone else. While a note shared *with* the user is open, `NoteEditor` sets `setSharedReferenceContext(noteId)` in `lib/notes/reference-resolver.ts`; whatever the user's own library can't resolve is asked again through that note — `resolveSharedReference` (jwpub-actions.ts) and `getSharedLinkedNote` (shares-actions.ts). Both go through `lib/notes/shared-context.ts`: the caller must have access to that shared note (`note_share_role`), the note's own HTML must carry that exact reference attribute (`citesAttribute`), and every service-role read is filtered to the owner's `user_id` — a shared note exposes exactly what it cites, never the library around it. A mentioned note is read-only in the panel (no "Abrir nota") and refused when locked directly or through a folder.
  - Recipients can **"Importar para mim"** (a full independent copy — a folder's whole tree, locked notes excluded, images copied into the importer's own Storage prefix and the bodies rewritten) and are then asked **"Cancelar compartilhamento?"** (leave the original or keep both). "Remover da minha lista" works without importing.
  - Images: a shared note mixes images under several users' prefixes, so `app/api/note-images/[...path]` also serves a path whose owner is linked to the viewer by an accepted share (`shares_connect`). The editor's image-diff cleanup does not run for shared notes (one client's diff could delete an image another just inserted), and the card's clickable checklist is disabled for them (it would write a stale body).
  - **Known gaps, deliberate**: ink, PDF annotations and audio are not shared/synced (they stay the owner's, local to the note); collapsing a heading (`collapsed` attribute) syncs to everyone; an image placeholder still uploading is visible to others; no end-to-end encryption (the Realtime channel carries plain text over TLS, same trust level as the server already has). The Supabase Realtime setting "Allow public access" can be turned off (nothing else uses Realtime) to force private channels project-wide.

# PWA / offline

- Offline support and installability run on `@serwist/turbopack` (Serwist 9), chosen specifically because it's Turbopack-native — it implements the service worker as a Route Handler (`app/serwist/[path]/route.ts`) instead of a bundler plugin, which is required since Next 16 defaults to Turbopack. Do not add `next-pwa` or the webpack-based `@serwist/next` — they don't work with `next build`'s default Turbopack pipeline here.
- Key files: `app/sw.ts` (service worker source — runtime caching via `defaultCache` from `@serwist/turbopack/worker`, offline fallback to `/offline`), `app/serwist/[path]/route.ts` (serves the built SW, lists explicit `additionalPrecacheEntries` for routes that must work offline even before a first visit — currently `/`, `/login`, `/offline`), `app/manifest.ts` (installable web app manifest), `app/install/` (the public install page, with platform-specific instructions and `beforeinstallprompt` capture).
- **Offline caching only activates in a production build.** `defaultCache`'s dev-mode branch is a hardcoded `NetworkOnly` for everything, and precache entries are disabled in dev (see `node_modules/@serwist/turbopack/src/index.worker.ts` and `src/lib/validate.ts`). `next dev` will register the service worker but it won't cache anything — to verify offline behavior, always run `npm run build && npm run start`, then use DevTools' Network → Offline (or an equivalent) after visiting the pages once.
- `proxy.ts`'s matcher excludes `/serwist` and `manifest.webmanifest` entirely (not just via `PUBLIC_ROUTES`) so fetching the service worker never triggers an auth cookie check. `/install` and `/offline` are in `PUBLIC_ROUTES` since they're real pages a signed-out (or offline) user must be able to reach.
- Adding a new route that should work offline on first install (not just after a visit): add it to `additionalPrecacheEntries` in `app/serwist/[path]/route.ts`. Anything else becomes available offline automatically after the user visits it once online (via the `pages`/`pages-rsc` runtime caches in `defaultCache`).
- A couple of `net::ERR_FAILED` console entries for `*?_rsc=...` prefetch requests while offline are expected — Next's Link prefetcher tries to warm RSC payloads for links on screen and fails silently when offline; it doesn't affect the actual page render or navigation.

- **Publications can be downloaded for offline reading** (`components/content/jwpub-offline-button.tsx` in the reader header; management in Settings → `offline-publications-card.tsx`). The reader's data comes from Server Actions, which the service worker can't cache, so a download copies the whole publication into **IndexedDB** (`lib/offline/idb.ts`, db `study-notes-offline`; `lib/offline/jwpub-offline.ts`): chapters, footnotes, embedded excerpts, the user's answers, and their highlights/notes. Server side it's read in budgeted slices (`getOfflineChapters/Footnotes/Extracts` in `jwpub-actions.ts`, `getPublicationHighlights` in `jwlibrary-actions.ts`) because a Server Action response is capped (~4.5 MB on Vercel). The publication row is written **last**, so an interrupted download never reads as "downloaded"; a row existing in the store *is* the "downloaded" flag, which is why `lib/offline/jwpub-data.ts` (the loaders the reader uses) just tries local first and falls back to the server. Reprocessing (↻) gives the publication a **new id**, so the old copy simply misses and the button offers "Baixar de novo".
  - Illustrations go to the Cache Storage bucket `jwpub-offline-media`, deliberately **not** the SW's `supabase-public-media` (capped at 200 entries, it would evict a download); `app/sw.ts` consults the offline cache first. Sign-out deletes the IndexedDB database and all of Cache Storage (`lib/sign-out-client.ts`).
  - Highlights, notes and "Sua resposta" edits go through **their own outbox** (`lib/offline/jwlibrary-outbox.ts`, persisted in localStorage `study-notes:jw-outbox`, rehydrated in `StoreHydration`) via `lib/offline/jwlibrary-mutations.ts` — every write is queued then replayed FIFO, online or not, from the same triggers as the notes outbox (`device-listener.tsx`). Rows are created with **client-chosen UUIDs** (`id`/`userMarkId` on `createJwlibraryNote`, `id` on `createJwlibraryHighlight`), so a later op can reference a row the server hasn't seen and a replay is idempotent (existing id → returns it). That replaced the reader's `optimistic:` temp ids; the Bible reader still uses them. Coalescing (`applyToQueue`): an edit folds into a queued create, a delete cancels a queued create, and an op currently in flight is never rewritten. A `Sessão expirada.` result keeps the op queued instead of dropping it. After the queue drains, `refreshOfflineUserData` re-reads marks/answers into the local copies and `JW_MARKS_CHANGED_EVENT` makes open readers reload.
  - **Not offline**: tags on highlight notes, cross-references into other publications, Bible citations, and the Bible reader's own highlights (the Bible isn't downloadable). They degrade with a message instead of an unhandled rejection. Offline navigation: `/notes/[id]` falls back to `/notes-offline`, whose `OfflineNoteView` renders `JwpubReader` from IndexedDB for a downloaded publication.
- **Folders can be moved** (menu "Mover para…" or dragging a folder card onto another / onto the open folder's back button). `setFolderParentRow` (`notes-actions.ts`) and the `0051_folder_cycle_guard.sql` trigger both refuse a cycle; the client checks first with `lib/folders.ts`. The move is a `setFolderParent` op under its own key `folder-parent:<id>` in the notes outbox. A rename/move of a folder whose `createFolder` is still unsynced is **folded into that create** (they share the `folder:<id>` slot, so queueing them separately overwrote the create). Locking is inherited through the tree, so moving a folder under a locked one hides its contents with no extra code.

# Security rules

- Never import `lib/supabase/server.ts` or `lib/supabase/admin.ts` into a Client Component — server-only Supabase clients and secrets must not reach the browser bundle. `admin.ts` (the service-role client, used for Storage) additionally imports the `server-only` package so this fails the build instead of silently shipping the key.
- The service-role client (`lib/supabase/admin.ts`) bypasses RLS entirely. Never call it before independently verifying the caller's session with the regular server client first, and never operate on a path/row without checking it actually belongs to that verified user — see the ownership check in `app/(app)/files-actions.ts` for the pattern to copy.
- `proxy.ts` is an optimistic check only (cookie presence), not the source of truth. Every Server Action and Route Handler that reads or mutates user data must independently verify the session via the server Supabase client — do not assume proxy already gatekept the request.
- Only `NEXT_PUBLIC_*` env vars may be referenced from Client Components. Any future secret (service role key, third-party API key) goes unprefixed and is only read in server-only files (Server Actions, Route Handlers, Server Components).
- Let `@supabase/ssr` manage the session cookies as-is (httpOnly, secure defaults) — don't hand-roll cookie parsing/writing for auth state.
- Validate and trim all form input server-side inside the Server Action itself (see the password-length check in `app/login/actions.ts`), even when the `<input>` already has client-side constraints like `required`/`minLength` — those are UX only, not security.
- Return generic error messages for auth failures (e.g. "E-mail ou senha incorretos.") — never leak whether an email exists in the system.
- Treat anything rendered from user-provided or third-party data (note content, file names, OAuth profile fields) as untrusted text, not markup.

- **The "@" menu also finds publications that aren't downloaded, through WOL** (`lib/notes/wol-query.ts` → `app/(app)/wol-lookup-actions.ts`). WOL's own search box (`/pt/wol/l/r5/lp-t?q=…`) understands *symbols*, never titles: "w05 1/6 16", "g88 8/12 10", "w24.11 9", "bh cap. 3", "lff lição 5" resolve to a card whose anchor carries the `MepsDocumentId`, so the row inserts an ordinary `pubref` reference and the existing chip/panel/"Baixar" flow does the rest. For a book the bare number is a **page**; `cap.`/`lição` are separate keywords. Names ("Achegue-se a Jeová 10") are mapped to symbols through `lib/notes/wol-catalog.ts`, generated by `node scripts/gen-wol-catalog.mjs` from WOL's public index. "Perspicaz <título>" reads the per-letter index page. The editor debounces this (250ms, with a "buscando…" row while it runs) and silently shows nothing offline. The endpoints are the site's own, not an API — if rows stop appearing, re-test `w05 1/6 16` (docId 2005404) first.

  - **Why the cited paragraphs are saved in the note.** A `pubref` chip created from a WOL lookup carries the cited paragraphs (`data-ref-pubref-snapshot`, entity-escaped so no raw `<`/`>` ever sits in an attribute — search, vectorization and scripture indexing strip tags with a plain `<[^>]+>` regex), taken from the card's `#h=<first>:…-<last>:…` paragraph range. The panel shows that copy at once and offline, with "Ver artigo inteiro" fetching the full article from WOL and "Baixar publicação" as the library route. A publication already in the library still wins over the copy. Book chapters have no paragraph range, so they get no copy and fetch live.
  - **A page citation opens on the cited paragraphs even when the publication is in the library** (`lib/notes/cited-excerpt.ts`, from the snapshot's `data-pid`s, with a header button for the whole chapter; printed page numbers show in the margin via `[data-page-markers] .pageNum` in globals.css, and the excerpt keeps the marker of the page it starts on); the panel header has a Subtítulos button opening them in a Vault (`chapter-subheadings.tsx`: `h2`/`h3`, `p.ss` in books).
  - **A page range can touch several articles** (`w03 15/3 20-25` returns the tail of the previous article and the one that really spans it), so `lookupWolReference` returns up to three, widest paragraph coverage first for a range and WOL's own order for a single page.
  - **An issue named without a page lists its articles** (`kind: "issue"` in `wol-query.ts` → `lookupWolIssue` → the menu's `issueMode`). WOL answers a page-less query with one card per document — the whole issue — but a card carries only the title; the start page is read from each article, where WOL prints `<span class="pageNum" data-no="N">` at every page break (smallest `data-no` = start page; `lib/notes/wol-issue.ts`). So it is one search plus one fetch per article (max 30, six at a time, all cached for an hour like the rest of this file), and rows come back in reading order with "w13 1/3 · p. 4" at their right. Forms verified live: `w13 1/3`/`w13 15/3` (semi-monthly to 2015 — a bare month expands to **both**), `w20.07`/`mwb20.07`, `g20.1`/`wp16.1`, `g 8/08` (monthly Despertai! 2006–2015; before that `g05 8/8` + `g05 22/8`), `km 5/08`, `yb13`, `od`; `wp13 1/3` and `w13.03` answer nothing (before 2016 the public Watchtower is the 1st-of-month `w` issue, so `wp` + month maps to that). Picking a row inserts the usual `pubref` chip with the article's `MepsDocumentId` and no saved paragraphs (it opens by fetching from WOL, like a book chapter). The menu scrolls and widens for these rows; an ordinary lookup is still capped at 7.
