# UI components

- Always build UI out of the primitives in `components/ui/` (`Button`, `Input`, `Field`, `Label`, `Checkbox`, `Alert`, `Badge`, `Tabs`, `Select`, `Textarea`, `Tooltip`, `Vault`, etc.). Do not drop down to raw `<button>`, `<input>`, `<label>` when an equivalent already exists there — add a variant or prop to the shared component instead of styling a one-off element inline.
- The whole app uses a single dark "Organic" theme (no light mode toggle exists yet): warm dark surfaces, pill-shaped controls, orange primary/accent. The tokens live in `app/globals.css` (`--background`, `--card`, `--primary`, `--accent`, `--success`, `--destructive`, `--border`, `--secondary`, `--muted`, `--ring`, `--surface`, `--surface-elevated`). Never hardcode hex colors in components — use the CSS variables (via Tailwind classes like `bg-primary`, `text-muted-foreground`, `border-border`) so a future palette change stays a one-file edit.
- Three font families are wired as Tailwind utilities: `font-heading` (Caprasimo — page titles, primary/outline CTA buttons), `font-sans` (Figtree — default body/UI text), `font-mono` (JetBrains Mono — small labels, badges, sync-status text). `Button`'s `default` and `outline` variants already apply `font-heading`; other variants stay `font-sans`.
- If a needed pattern doesn't exist yet in `components/ui/`, extend the existing component (new `variant`/`size` in its `cva` config) rather than forking it, so every consumer benefits and the design stays in one place.
- **No modal dialogs, ever — confirmations go through a Vault.** This app has no `Dialog`/`AlertDialog` component and shouldn't gain one. Any "are you sure?" moment (delete note, delete folder, bulk delete, …) uses `components/ui/confirm-vault.tsx` (`<ConfirmVault>`), which is already mobile/desktop-adaptive because it's built on `Vault`. If a new confirmation need doesn't fit `ConfirmVault`'s props, extend that component rather than reaching for a dialog primitive.

# Architecture

- Next.js App Router only, on Next.js 16 — this version renamed `middleware.ts` to `proxy.ts` and made several other breaking changes from what most training data assumes. Before touching routing, caching, or config, check `node_modules/next/dist/docs/` for the current API (see `AGENTS.md`).
- Auth is Supabase (`@supabase/ssr`), split by runtime:
  - `lib/supabase/client.ts` — browser client, for Client Components only.
  - `lib/supabase/server.ts` — server client (reads/writes cookies via `next/headers`), for Server Components, Server Actions, and Route Handlers.
  - `lib/supabase/middleware.ts` + `proxy.ts` — refreshes the session on every request and does the optimistic redirect between public/protected routes. Public routes are listed in `PUBLIC_ROUTES` in `lib/supabase/middleware.ts`.
- Mutations (sign in/up/out, and future data writes) go through Server Actions (`"use server"`), colocated as `actions.ts` next to the page that uses them (see `app/login/actions.ts`), driven from the client with `useActionState`. Prefer this over client-side `fetch` to an API route.
- Auth is email/password only — no OAuth providers (Google, etc.) are wired up, and none should be added unless explicitly requested. `app/auth/callback/route.ts` still exists for exchanging the code from Supabase's e-mail confirmation links (signup confirmation), not for OAuth.
- New protected areas of the app go under routes added to the protected side of `proxy.ts`'s route check; new public marketing/auth pages go in `PUBLIC_ROUTES`.
- Signed-in app screens live in the `app/(app)/` route group, which supplies the sidebar + assistant surface via its layout. Its pages compose `<Header variant="search|title">` + content + (where relevant) `<AssistantDock />`.
- Notes, files and folders all share the single `/notes` screen — there is deliberately **no** separate `/files` route. `<NotesCollection showFolders />` renders the folders row plus the mixed notes/files masonry; clicking a folder filters in place via local state rather than navigating.
- Notes and folders are real Postgres tables (`public.notes`, `public.folders`) — **RLS is the actual access control here**, unlike Storage (see below). Every row has `user_id`, and both tables have an owner-only `for all using (auth.uid() = user_id)` policy, so `app/(app)/notes-actions.ts` uses the regular per-request server client (`lib/supabase/server.ts`), not the admin client — Postgres itself rejects cross-user reads/writes even if a check in app code were ever missed.
- **`lib/store/notes-store.ts` is offline-first**, not just an optimistic cache: it's a zustand store wrapped in `persist` (localStorage, key `study-notes:notes`, `skipHydration: true` — rehydrated explicitly by `StoreHydration`), holding `notes`, `folders`, and a **pending-ops outbox** (`pendingOps`, keyed so a burst of edits to the same note/folder coalesces into one queued op instead of stacking). Every mutation still updates state optimistically first, then calls the matching Server Action via `runOrQueue`: a normal `{error}` response is a real rejection (rolls back + toasts, as before); a **thrown** error means the `fetch()` itself never reached the origin (offline), so the op is written into `pendingOps` instead of surfaced as a failure. `updateNote` never rolls back note text either way — discarding what the user just typed would be worse than a stale save.
  - Coalescing rules live in `enqueueOp`: a second `updateNote` for the same id replaces the first in place; a `deleteNote`/`deleteFolder` queued behind an unsynced `createNote`/`createFolder` for the same id cancels both out rather than round-tripping a doomed create-then-delete.
  - Reconnection is driven from three places in `components/providers/device-listener.tsx` (all calling `useNotesStore.getState().syncPendingOps()`, which replays the outbox in FIFO order and stops at the first op that still can't reach the server): the browser's `online` event, a `focus`/`visibilitychange` fallback (the `online` event is not reliable everywhere — confirmed empirically in Playwright's network-offline emulation, where toggling a context back online does not fire it for a page created while already offline), and a 5s `setInterval` safety net that only does anything when `pendingOps` is non-empty. `useDeviceStore.isOnline` (mirrored from `navigator.onLine`) drives the sidebar's connectivity copy; `usePendingSyncCount()` drives its "N alterações aguardando sincronização" line — this is the real `design.html` mockup's original intent for that card, not new scope.
  - `StoreHydration` calls `useNotesStore.persist.rehydrate()` **before** `hydrate(serverNotes, serverFolders)`, so `hydrate`'s merge can tell which ids have a pending op and keep the local version for those (including notes/folders that only exist locally — an unsynced create) instead of letting the server-fetched rows clobber an unsynced draft. Anything with a pending delete is dropped from the merge even if the server still has it.
  - **Deliberately not using `experimental.useOffline`** (Next 16's built-in connectivity-aware retry for navigations/Server Actions, `next/offline`): tried it first, but it holds a Server Action's `fetch()` pending *in memory* instead of rejecting, which defeats `runOrQueue`'s catch-based detection — nothing ever lands in the persisted outbox, so an edit made offline is lost for good if the tab closes before reconnecting (verified this empirically before reverting). Our own outbox is strictly more durable for this app's requirement (drafts must survive a closed/reloaded tab), so the flag stays off.
  - **Known gap**: creating a brand-new note via the assistant dock's press-and-drag gesture, starting from a session that has been offline the *entire* time (never navigated to `/notes/new` while online this session), doesn't render the editor until reconnection — `/notes/new` and `/notes/[id]` sit under the `(app)` layout's per-request `listUserContent()` fetch, which makes the whole subtree a dynamic route Next can't serve from a client-side navigation without a network round trip. `AssistantDock` calls `router.prefetch("/notes/new", { kind: "full" })` on mount to paper over this for the common case (opened the app online this session, then went offline), but a genuinely cold-offline session still shows nothing until the connection returns — verified no data is lost either way (the drafted text rides in the `?q=` search param and the note is created normally once the deferred navigation resolves), just delayed. Fixing this fully would mean moving `listUserContent()` off the shared layout (Cache Components/Partial Prefetching, per `node_modules/next/dist/docs/01-app/02-guides/offline-support.md`) — not done here.
- **Schema changes go through `scripts/db-migrate.mjs`**, which applies any new `.sql` file in `supabase/migrations/` (tracked in a `public._migrations` table, filename order, one transaction each) using `DATABASE_URL` — a direct Postgres connection string (Project Settings → Database), not the Supabase REST API, since RLS policies and other DDL aren't reachable through `service_role`/PostgREST. Add a new numbered file rather than editing an applied one. Run it with `npm run migrate`.
- Initial notes/folders are fetched **server-side** in the async `app/(app)/layout.tsx` (via `listUserContent()`, RLS-scoped to the signed-in user) and passed into `<StoreHydration>`, which seeds the zustand store once on mount. `useHydrated()` reflects the store's own `hydrated` flag, not "some component mounted" — child effects fire before parent effects in React, so a mount-based flag in a child could (and did, before this was fixed) flip true before the parent's seeding effect had actually run.
- **Notes are rich text**, via Tiptap (`components/content/rich-text-editor.tsx`), storing HTML in the same `notes.body` column that used to hold plain text (no migration needed — Tiptap renders plain text as a single paragraph, so old notes still load fine). Formatting is a **floating `BubbleMenu`** (from `@tiptap/react/menus`, not a fixed toolbar) that appears on text selection: bold, italic, task list, and text-align left/center/right/justify. Image insert lives as a persistent header button next to the pin button in `note-editor.tsx` (not the bubble menu, which only shows when text is selected) — plus paste and drag-and-drop, both handled in `editorProps.handlePaste`/`handleDrop`.
  - `TaskList`/`TaskItem` **must** come from `@tiptap/extension-list`, not the older standalone `@tiptap/extension-task-list`/`@tiptap/extension-task-item` packages — StarterKit already wires up `@tiptap/extension-list`'s `ListKeymap`, which those standalone packages don't share, and without it Enter did nothing inside a bullet/ordered list item (not applicable to `taskItem` either way, see the known gap below).
  - **Known gap, verified not worth the fix cost**: pressing Enter while the cursor is inside an existing task item does not create a new task item (`editor.commands.splitListItem("taskItem")` returns `false` even with a cleanly collapsed selection — reproduced directly against the editor instance, not a test artifact). The working pattern instead: type each item as its own line first, then select all of them and toggle "Lista de tarefas" once — `toggleTaskList` correctly turns every selected paragraph into its own item. Enter still works completely normally everywhere else (plain paragraphs split fine).
  - Images upload through `app/(app)/note-images-actions.ts` (`uploadNoteImage`) to a **second, public-read** Storage bucket, `note-images` — deliberately separate from the private `files` bucket below, because an inline `<img src>` needs a stable long-lived URL and `files`' signed URLs expire in 60s. Public read only; writes still require the service-role client (`createAdminClient()`), same ownership-by-path-prefix convention as `files`. Provisioned via a one-off script (not a SQL migration — Storage buckets aren't DDL) with `public: true`.
  - **Orphaned images are cleaned up**, via `lib/note-images.ts` (`extractNoteImagePaths`/`removedNoteImagePaths` — regex-based, not `DOMParser`, since this needs to run server-side too) and `deleteNoteImages` in `note-images-actions.ts`: deleting a note (`deleteNotePermanently`/`bulkDeleteNotesPermanently` in `notes-actions.ts`) removes every image still referenced in its body; editing a note's body (`updateNote` in `notes-store.ts`) diffs the old vs. new body **client-side** (both are already in memory there, avoiding an extra server round trip on every autosave) and deletes whatever image got removed from the text. Both are best-effort and fire-and-forget — not part of the offline outbox, since a failed cleanup just leaves an orphaned object (reclaimable bytes), never lost note content, so it doesn't need the outbox's retry/durability guarantees.
  - Card previews (`components/content/note-card.tsx`) parse the HTML body client-side via `lib/note-preview.ts` (`DOMParser`, safe here since `NoteCard` only ever renders after the notes store has hydrated, i.e. always client-side) into whichever of three views a card shows: a Keep-style checklist (up to 5 items, "+N mais" beyond that, struck-through when checked) if the body contains a task list; a leading image thumbnail if it contains an image and no task list; otherwise a truncated excerpt that **preserves inline formatting** (`truncateToHtml` walks the DOM keeping `<strong>`/`<em>`/etc. intact instead of just reading `textContent`, then it's rendered via `dangerouslySetInnerHTML` — safe here since the body is Tiptap-schema HTML, the same trust level `NoteEditor` already renders it at, not arbitrary markup). File-type cards (PDF/DOCX/etc.) skip all of this — their `body` is a plain one-line size string like "2.3 MB", never HTML.
  - Checklist items are **directly clickable from the card preview** (`onToggleChecklistItem` prop, wired through `notes-collection.tsx` to `useNotesStore.toggleChecklistItem`, which flips the item's `data-checked`/`checked` attributes via `lib/note-preview.ts`'s `toggleChecklistItemInHtml` and reuses `updateNote`'s normal offline-safe save path). Each item is its own `<button>`, structurally a **sibling** of the card's title-opening `<button>` — not nested inside it — specifically so clicking a checkbox can never also trigger "open the note" and so the markup stays valid (a checkbox can't nest inside another button).
  - The editor's task-item checkbox is a custom React node view (`components/content/task-item-node-view.tsx`, wired via `TaskItem.extend({ addNodeView: () => ReactNodeViewRenderer(...) })` in `rich-text-editor.tsx`) using the app's own animated `Checkbox` primitive (`components/ui/checkbox.tsx`) instead of Tiptap's default bare native `<input type="checkbox">`. `NodeViewWrapper` must be given `as="li"` — its default tag is `div`, which would break the list's actual DOM structure.
- The assistant (`components/assistant/`) is UI-complete but talks to a **placeholder** server action (`app/(app)/assistant-actions.ts`) — no AI provider key is configured. It still verifies the Supabase session server-side, and returns the `AssistantReply` shape the real RAG call should keep.
- Uploaded files are real, in Supabase Storage — the private `files` bucket (`user_id/uuid-filename` paths, no bucket-level RLS policies since every access goes through the service-role client server-side; verified empirically — direct anon upload/list/download attempts against the bucket all fail even with a real object present, since `storage.objects` RLS defaults to deny-all with zero policies). `app/(app)/files-actions.ts` has the only code allowed to touch it: `uploadFiles` (validates size/extension/rate-limit, uploads, then inserts the matching `notes` row via the regular per-user client in the same call), `getFileUrl` (60s signed URL), `deleteStorageFile`. All three re-verify the session and check the path is prefixed with that user's id before doing anything — the bucket has no RLS of its own, so this ownership check *is* the access control for Storage specifically (contrast with notes/folders above, where RLS itself is the control). `hooks/use-file-upload.ts` is the one client entry point (used by the mobile upload button and desktop drag-and-drop); everything else (limits, bucket name) lives in `lib/storage-config.ts`. Size limits are per-extension via `maxSizeForExtension()` — `.jwpub` gets 60 MB (a whole publication) against the 15 MB default, still inside the 80 MB `serverActions.bodySizeLimit`/`proxyClientMaxBodySize` pair.
- **`.jwpub` publications are read in-app, not downloaded.** A `.jwpub` is a zip wrapping a SQLite database (sometimes nested inside a `contents` entry that is itself a zip) plus media; `Document`/`Footnote` blobs are AES-CBC encrypted then deflated, keyed by `SHA-256("{MepsLanguageIndex}_{Symbol}_{Year}[_{IssueTagNumber}]")` XOR a fixed constant (bytes 0..16 = key, 16..32 = IV — and the `_{IssueTagNumber}` segment is omitted when it's 0, which is the single easiest thing to get wrong).
  - **Parsing runs in the browser** (`lib/jwpub/`), because it needs `DOMParser` — which Node lacks — plus `sql.js`/`pako`/`crypto.subtle`, and because re-sending a 60 MB archive to the server would be a second upload. `jszip`/`sql.js`/`pako` are pulled in *only* via `await import(...)` inside `lib/jwpub/parser.ts` (the repo's only dynamic import), so they land in a lazy chunk the reader never loads — verified absent from `build-manifest.json`'s root files.
  - **Ingest is fire-and-forget from `hooks/use-file-upload.ts`**, after `uploadFiles` + `addFiles` have already put the card on screen. That ordering is deliberate: the note row and Storage object exist before parsing starts, so any parse failure just leaves a normal file card plus a `status = 'failed'` publication row, and the reader offers "Processar publicação" — which re-downloads via `getFileUrl` and re-runs the same `ingestJwpub`. That retry is also the path for files uploaded before this feature existed.
  - Parsed content lives in `jwpub_publications` / `jwpub_chapters` / `jwpub_footnotes` (migration `0002`), **deliberately unencrypted** unlike `notes` — public publication material, still RLS-scoped per owner. Everything cascades from `notes.id`, so deleting a note drops the whole publication; only Storage needs the explicit sweep (`deletePublicationMediaForNote`, wired into `deleteNotePermanently`/`bulkDeleteNotesPermanently`).
  - Illustrations go to the public-read `jwpub-media` bucket under `${user_id}/${publication_id}/`, uploaded in batches of `JWPUB_MEDIA_BATCH_SIZE`, deduped by filename, and only for images a chapter actually references. **Images pulled out of a zip arrive typeless**, and Supabase validates the bucket's `allowedMimeTypes` against the blob's own type, not the `contentType` option — so `uploadPublicationMedia` re-wraps each file in a `Blob` with the extension-derived type before uploading. Without that every upload fails with `mime type application/octet-stream is not supported`.
  - `jwpub-media://` refs are rewritten to real URLs and `jwpub://f/<id>` links converted to `data-jwpub-footnote` attributes **at ingest, before sanitizing with DOMPurify and persisting** — so the database only ever holds trusted markup, the reader is a plain renderer, and DOMPurify never has to allow an exotic URI scheme. `jwpub://b/…` and `jwpub://p/…` become inert `data-jwpub-ref` (reference resolution isn't implemented).
  - The reader lives at `/notes/[id]`: that page asks `getPublication(id)` and renders `<JwpubReader>` when a publication exists, else `<NoteEditor>`. `openNote()` in `notes-collection.tsx` routes `type === "jwpub"` there instead of opening a signed URL. Footnotes follow the assistant's surface pattern — `Vault` on mobile, side panel on desktop, never a modal.
  - `public/sql-wasm.wasm` (0.63 MB) is served locally rather than from a CDN, comfortably under Serwist's 2 MiB precache cap.
- Screens/pages use `framer-motion` for entrance and transition animations (already a dependency) — fade/slide the page or card in on mount, stagger hero/list children, and cross-fade state changes like the sign-in/sign-up toggle (see `app/login/login-form.tsx` and `app/page.tsx`). Server Components that need animation wrap just the animated part in a small client component (see `components/ui/fade-in.tsx`) rather than converting the whole page to a Client Component.

# PWA / offline

- Offline support and installability run on `@serwist/turbopack` (Serwist 9), chosen specifically because it's Turbopack-native — it implements the service worker as a Route Handler (`app/serwist/[path]/route.ts`) instead of a bundler plugin, which is required since Next 16 defaults to Turbopack. Do not add `next-pwa` or the webpack-based `@serwist/next` — they don't work with `next build`'s default Turbopack pipeline here.
- Key files: `app/sw.ts` (service worker source — runtime caching via `defaultCache` from `@serwist/turbopack/worker`, offline fallback to `/offline`), `app/serwist/[path]/route.ts` (serves the built SW, lists explicit `additionalPrecacheEntries` for routes that must work offline even before a first visit — currently `/`, `/login`, `/offline`), `app/manifest.ts` (installable web app manifest), `app/install/` (the public install page, with platform-specific instructions and `beforeinstallprompt` capture).
- **Offline caching only activates in a production build.** `defaultCache`'s dev-mode branch is a hardcoded `NetworkOnly` for everything, and precache entries are disabled in dev (see `node_modules/@serwist/turbopack/src/index.worker.ts` and `src/lib/validate.ts`). `next dev` will register the service worker but it won't cache anything — to verify offline behavior, always run `npm run build && npm run start`, then use DevTools' Network → Offline (or an equivalent) after visiting the pages once.
- `proxy.ts`'s matcher excludes `/serwist` and `manifest.webmanifest` entirely (not just via `PUBLIC_ROUTES`) so fetching the service worker never triggers an auth cookie check. `/install` and `/offline` are in `PUBLIC_ROUTES` since they're real pages a signed-out (or offline) user must be able to reach.
- Adding a new route that should work offline on first install (not just after a visit): add it to `additionalPrecacheEntries` in `app/serwist/[path]/route.ts`. Anything else becomes available offline automatically after the user visits it once online (via the `pages`/`pages-rsc` runtime caches in `defaultCache`).
- A couple of `net::ERR_FAILED` console entries for `*?_rsc=...` prefetch requests while offline are expected — Next's Link prefetcher tries to warm RSC payloads for links on screen and fails silently when offline; it doesn't affect the actual page render or navigation.

# Security rules

- Never import `lib/supabase/server.ts` or `lib/supabase/admin.ts` into a Client Component — server-only Supabase clients and secrets must not reach the browser bundle. `admin.ts` (the service-role client, used for Storage) additionally imports the `server-only` package so this fails the build instead of silently shipping the key.
- The service-role client (`lib/supabase/admin.ts`) bypasses RLS entirely. Never call it before independently verifying the caller's session with the regular server client first, and never operate on a path/row without checking it actually belongs to that verified user — see the ownership check in `app/(app)/files-actions.ts` for the pattern to copy.
- `proxy.ts` is an optimistic check only (cookie presence), not the source of truth. Every Server Action and Route Handler that reads or mutates user data must independently verify the session via the server Supabase client — do not assume proxy already gatekept the request.
- Only `NEXT_PUBLIC_*` env vars may be referenced from Client Components. Any future secret (service role key, third-party API key) goes unprefixed and is only read in server-only files (Server Actions, Route Handlers, Server Components).
- Let `@supabase/ssr` manage the session cookies as-is (httpOnly, secure defaults) — don't hand-roll cookie parsing/writing for auth state.
- Validate and trim all form input server-side inside the Server Action itself (see the password-length check in `app/login/actions.ts`), even when the `<input>` already has client-side constraints like `required`/`minLength` — those are UX only, not security.
- Return generic error messages for auth failures (e.g. "E-mail ou senha incorretos.") — never leak whether an email exists in the system.
- Treat anything rendered from user-provided or third-party data (note content, file names, OAuth profile fields) as untrusted text, not markup.
